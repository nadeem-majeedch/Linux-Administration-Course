# Contributing to the Linux Administration Course

Thanks for improving this course! Contributions come from instructors, TAs, students,
and practitioners. This document explains what we accept and how we review it.

## Code of Conduct

Be patient with beginners. This repository exists to teach people with **zero Linux
experience**. Assume good faith, explain rather than gatekeep, and keep examples
professional. Harassment or condescension toward learners is not tolerated; reports
go to the course maintainer listed in the repository metadata.

## How to Contribute

1. **Open an issue first** for anything larger than a typo fix — curriculum changes,
   new modules, new datasets, or changed lab workflows need maintainer sign-off
   before you invest hours in them.
2. **Fork or branch** from `main` using a descriptive branch name:
   `fix/m12-chmod-typo`, `feature/m08-extra-regex-labs`, `content/m24-incident-4`.
3. **Keep commits small and described** — the course itself grades Git hygiene (M26),
   so this repository models the behavior it teaches.
4. **Submit a pull request** referencing the issue; describe what changed and why.
5. **Respond to review feedback**; at least one maintainer review is required for
   content changes.

## What We Accept

| Type | Examples |
|---|---|
| Fixes | command typos, wrong flags, broken links, factual corrections |
| Lab improvements | clearer steps, better expected outputs, extra checkpoints |
| New exercises | additional drills consistent with a module's difficulty level |
| Datasets | small (≤ ~10 MB), synthetic or properly licensed, with documentation |
| Cheatsheets & glossary entries | plain-language, accurate, course-scoped |
| Translations | of README/SETUP, tracked as `README.<lang>.md` |

## What We Don't Accept

- **Content encouraging unsafe practice:** destructive commands without safeguards,
  disabling firewalls/updates "to make things work," credential sharing, or
  `curl | sudo bash`-style patterns presented as normal.
- **Distro-drift:** commands presented as universal when they are Ubuntu-specific,
  without a note (see Style Rules below).
- **Fabricated tooling:** commands, flags, or behaviors that cannot be verified
  against official documentation (Ubuntu man pages, kernel.org docs, GNU manuals,
  systemd docs). If you can't cite it, don't submit it.
- **Unlicensed datasets** or datasets containing real personal data.
- **Large binaries** (ISOs, VM images, model weights) — link officially instead.

## Style Rules for Content

These keep 30 modules coherent; reviewers enforce them:

1. **Audience:** write for a student with zero Linux experience on their first read;
   never assume a concept taught in a later module.
2. **Environment:** primary environment is **Ubuntu LTS**. When a command is
   distro-specific, add a one-line note for Debian/others (e.g., dnf/pacman
   equivalents) — see the translation table convention in M16.
3. **No root assumption:** labs must work for a normal user in the course VM; steps
   needing sudo are marked `sudo` explicitly with a one-line why.
4. **Safety fencing:** any destructive command (`rm -rf`, `mkfs`, `parted`, `dd`,
   `--delete`, `crontab -r`, `docker system prune`) appears with: what it destroys,
   the safeguard (snapshot/dry-run/backup), and the recovery path.
5. **Verify everything:** every command in a lab must have been run on Ubuntu LTS;
   expected outputs must be real outputs (trimmed, not invented).
6. **Data Science connection:** every module keeps its "DS connection" section
   current when content changes.
7. **Formatting:** Markdown, one sentence per line is welcome (semantic line
   breaks); tables for structured facts; fenced code blocks with language hints
   (`bash`, `python`, `text`).
8. **Module template:** new/edited modules follow
   [modules/M01-what-is-linux/README.md](modules/M01-what-is-linux/README.md)
   section order exactly.

## Module Template Checklist

Before submitting a module or major module edit:

- [ ] Overview, Prerequisites, Difficulty present
- [ ] Learning objectives are observable actions ("can do X"), not topics
- [ ] Concepts section teaches the mental model, not just commands
- [ ] Command-line skills list every command the lab uses
- [ ] Laboratory has numbered steps, expected outputs, and a checkpoint
- [ ] Exercises include at least 6 items and where solutions live
- [ ] Mini-project present or explicitly "none" with reason
- [ ] DS connection section exists and is concrete
- [ ] Common pitfalls + self-check present
- [ ] Further reading links to official docs only
- [ ] Prerequisite chain respected (no forward references to later modules)

## Dataset Contributions

- Prefer synthetic data generated by a committed script (reviewable, reproducible).
- Real data must be publicly licensed (e.g., Open Data Commons, CC0) with the
  license and provenance stated in `datasets/<name>/README.md`.
- Size guideline: a module's dataset should clone in seconds; larger ones belong in
  generation scripts or external sources with checksums.
- Include a schema and a "known quirks" section (delimiters, encodings, dirty rows) —
  dirty-on-purpose data is a feature; undocumented dirtiness is not.

## Review Process

- **Typos/links:** one maintainer merge.
- **Lab/content changes:** two reviews (one content, one technical accuracy).
- **New modules or unit restructuring:** maintainer decision after issue discussion;
  changes to the module count or order require updating `README.md`,
  `COURSE-ROADMAP.md`, and all cross-references in the same PR.
- CI (when configured) runs link checks and Markdown lint; green CI is expected
  before review.
