## 1. Remotes: history with a second home

Everything in Lessons 1–2 lived inside one machine's `.git/` directory. A
**remote** is simply another copy of the repository that your repo knows
about, referenced by a short name (conventionally `origin`). A remote is not
special infrastructure — it's just *another repository* yours syncs with.

The lab trick that makes this module network-free: the remote can be a
**bare repository on your own VM**. A bare repo is a `.git`-style directory
with no working tree — nobody edits files there; it exists only to receive
and serve history. It is exactly what a Git server (GitHub, GitLab, or the
department's own GitLab instance) is, minus the web interface:

```console
$ git init --bare ~/repos/sales-analysis.git
$ cd ~/projects/sales-analysis
$ git remote add origin ~/repos/sales-analysis.git
$ git remote -v
origin  /home/ds/repos/sales-analysis.git (fetch)
origin  /home/ds/repos/sales-analysis.git (push)
```

With that in place, the sync pair:

- **`git push origin main`** — upload commits your repo has that the remote
  lacks. Technically: transfer objects, then update the remote's `main`
  pointer.
- **`git pull origin main`** — fetch the remote's new commits *and* merge
  them into your current branch. (`git fetch` does only the download — the
  polite way to *look* before integrating.)

When both sides advanced, push is **rejected** — Git refuses to guess how
your history and the remote's should combine:

```console
 ! [rejected] main -> main (fetch first)
error: failed to push some refs ...
```

The fix is the lesson: `git pull`, resolve anything that conflicts
(Lesson 2 §4), *then* push. Pull-merge-push is the daily loop on every
shared repository you'll ever touch.

`git clone <url>` is remote-setup from the other direction: it copies a
remote's whole history and pre-configures `origin` for you. Cloning the
course's own materials (or a teammate's repo) is the everyday case.

## 2. `.gitignore`: deciding what history forgets

Git tracks what you `git add` — which means *you* decide what belongs in
history. Some things never do:

| Never commit | Why | M27 tie-in |
|---|---|---|
| `.venv/` | rebuildable from `requirements.txt`; thousands of files, machine-specific | environments are files, not history |
| `data/` (raw, large) | datasets don't belong in VCS — huge, often licensed, changes by re-download | keep a `data/README.md` describing provenance instead |
| `outputs/`, `*.log` | derived artifacts, regenerated by running the pipeline | reproducible pipelines re-earn their outputs |
| `.ipynb_checkpoints/` | Jupyter's autosave debris | commit the notebook, not its checkpoints |
| `.env`, `*.pem`, `credentials*` | **secrets** — M25's rule | committing a key is an incident, not a typo |

A `.gitignore` at the repo root, one pattern per line:

```gitignore
# environments & caches
.venv/
__pycache__/
.ipynb_checkpoints/

# data & derived artifacts
data/raw/
data/processed/
outputs/
*.log

# secrets — never, ever
.env
*.pem
*.key
```

Behavior worth knowing precisely:

- Ignored files show in `git status` only in the summary count; add
  `git status --ignored` to see them.
- `.gitignore` **does not untrack already-committed files** — if `data.csv`
  was committed before you wrote the ignore rule, `git rm --cached
  data.csv` (untrack, keep on disk) + commit is the cure. Prevention is the
  real fix: write `.gitignore` *first*, before the first `git add`.
- `git add data/big.csv` by explicit name **overrides** the ignore — a
  feature (deliberate exceptions), and a footgun. `git add -A` respects the
  file; blind explicit adds don't check it.

**The commit `.gitignore` itself** — it's project documentation, and every
collaborator needs the same exclusions.

## 3. SSH-authenticated remotes: the university-server pattern

Every remote URL answers two questions: *where* is the repo, and *how do I
prove I'm me?*

```
https://gitlab.example.com/team/project.git    ← HTTPS: password/token per push
git@gitlab.example.com:team/project.git        ← SSH: your key pair (M22 §1)
```

The SSH form is what you already speak. The server holds your **public**
key in its `authorized_keys`; your **private** key (passphrase-protected,
carried by `ssh-agent`) proves identity without sending anything
reusable over the wire. Because the key was already set up for
`ssh ds@gpu-server` in [M22](../../../M22-ssh-remote-admin/README.md), the very
same key authenticates Git over the same sshd — one credential, one habit.

Test the exact way you test any SSH host:

```console
$ ssh -T git@gitlab.example.com
Welcome to GitLab, @adaokoye!        # server recognized your key
```

A local-bare-repo remote (§1) skips authentication entirely — same user,
same machine — which is why Labs use it. When you later point `origin` at
the university GitLab, nothing new is needed beyond the URL: agent running,
key loaded (`ssh-add -l` to check), push.

Which to choose? **SSH** on machines with your key (your VM, the GPU
server you administer); **HTTPS + token** elsewhere (borrowed machines,
CI systems) — a token is revocable without touching key infrastructure.
Never paste a password into a remote URL or a script; M25 §5's secrets
rules apply to Git verbatim.

## 4. Workflows: how teams actually use branches

Solo and team usage differ in ceremony, not mechanics:

**Solo (trunk-based-ish).** Commit small and often to `main`; branch only
for risky experiments (`git switch -c try-polynomial`); merge when the
experiment wins, delete the branch when it loses. History stays linear and
honest. This is *your* repo's workflow all module.

**Small team (feature branches).** One branch per unit of work, named for
it (`feature/region-summaries`, `fix/dtype-revenue`):

1. `git switch -c feature/region-summaries` (fresh off `main`)
2. commit in small steps with *why*-messages
3. `git pull origin main` — integrate others' work early, conflicts stay
   small
4. `git push origin feature/region-summaries`
5. a teammate reviews; merge to `main` (on GitLab: a *merge request* —
   same merge mechanics as Lesson 2, with a conversation attached)
6. delete the branch; `main` is again known-good

Two habits carry the whole pattern: **pull before you start** (begin from
everyone else's work) and **pull before you push** (the rejection from §1
means someone landed work while you were heads-down — integrate, don't
force). For data science specifically: notebooks get committed like any
other file, but *clear outputs before committing* (`nbconvert --clear-output`
or the Jupyter UI) — 40 MB of embedded plot PNGs per commit is how repos
become unusable.

## Key takeaways

- A **remote is just another repo**; a bare repo on your own machine is a
  complete, network-free stand-in for a Git server.
- **push/pull/fetch** transfer and update pointers; a rejected push means
  *pull first*.
- **`.gitignore` first**, and never commit venvs, datasets, outputs, or
  secrets — untracking is possible, un-sending is not.
- **SSH remotes** reuse your M22 key pair; HTTPS+token is the portable
  alternative.
- Solo work stays trunk-based; teams use feature branches with
  pull-early-pull-before-push discipline.

## Check yourself

1. What is a bare repository, and why does a Git server use bare repos?
2. Your push is rejected with "fetch first". What happened, and what are
   the next two commands?
3. `data.csv` is committed and *then* added to `.gitignore`. Does Git stop
   tracking it? What's the fix?
4. Why is the same SSH key valid for both `ssh ds@server` and `git push`
   to a repo on that server?

*Answers:* (1) a repo with no working tree — receives/serves history only;
no working tree means no one can edit "on the server side", which keeps
syncs unambiguous. (2) the remote gained commits you don't have;
`git pull origin main` (resolve if needed), then `git push origin main`.
(3) no — ignore rules affect untracked files; `git rm --cached data.csv` +
commit. (4) both are sshd authenticating with the same `authorized_keys`
entry — Git-over-SSH is just an SSH session restricted to Git commands.
