# Lab 3 — Monitoring Under Load: Reading One Machine Three Ways

> Module 24 · Unit 6 · Difficulty: Advanced
> Time: ~45 min · Environment: your own VM
> Prerequisites: [Lesson 3](../lessons/03-monitoring-toolkit.md), M18's
> stress habits, `sudo apt install sysstat` (the M16 five-beat
> workflow — read-only lab otherwise)
> ⚠️ Load is generated by *this lab's own scripts*, capped to a few
> minutes. Nothing is installed beyond sysstat; no system services are
> touched.

One workload, watched by three instruments — `vmstat`, `iostat`,
`sar` — each read and interpreted in `lab-log.md`. The point is not
the numbers; it's knowing *which instrument answers which question*.

## Setup — the workload (5 min)

Two files in `~/lab24/`:

**`burn.sh`** — CPU load, one worker per run, politely niced:

```bash
#!/usr/bin/env bash
# burns CPU for $1 seconds, 1 worker, nice 19 (M18's courtesy)
timeout "${1:-60}" nice -n 19 bash -c \
  'while :; do :; done' &
wait
```

**`churn.sh`** — I/O load: writes then re-reads a 200 MB file:

```bash
#!/usr/bin/env bash
# $1 = seconds of write+read churn
F=~/lab24/churnfile
timeout "${1:-60}" bash -c "
  while :; do
    dd if=/dev/zero of=$F bs=1M count=200 status=none
    cat $F > /dev/null
  done" &
wait
```

```console
$ chmod +x burn.sh churn.sh
$ df -h ~ | tail -1        # 200 MB scratch fits? (if not: bs=1M count=100)
```

## Baseline — record healthy first (5 min)

No load running:

```console
$ nproc && uptime
$ vmstat 2 3            # note: r, si/so, us, id, wa
$ free -h
$ df -h ~ | tail -1
```

Record this block in `lab-log.md` as **BASELINE**. Every later
reading is interpreted *against* it — a "high" number with no
baseline is just a number.

## Round 1 — CPU load through vmstat (10 min)

Terminal 1: `./burn.sh 180` (3 minutes).
Terminal 2, starting ~30s in:

```console
$ vmstat 2 8
```

Watch `r` (runnable) climb toward/past core count and `us` swell
while `id` collapses. Record: two consecutive samples mid-load.

**Interpret to write:** is this *utilization* (yes — us high), and is
it *saturation* (compare `r` to `nproc`)? One sentence: why does this
load make `wa` ~0? (Hint: what resource is burn.sh *not* using?)

Stop check: `./burn.sh` exits on its own (`timeout`); verify with
`pgrep -af burn.sh` that nothing lingers.

## Round 2 — I/O load through iostat (10 min)

Reset ~1 min. Terminal 1: `./churn.sh 180`.
Terminal 2:

```console
$ iostat -x 2 6        # find your root/home disk device (likely vda or sda)
```

Record mid-load: `%util`, `await`, `wkB/s`+`rkB/s` for the busy
device. Then — the diagnostic pivot — watch **vmstat at the same
time**:

```console
$ vmstat 2 5           # note: wa now nonzero, b possibly nonzero
```

**Interpret to write:** three sentences — (1) which device carried
the load, (2) what `%util`/`await` say about *saturation* at the
device axis, (3) what `wa` climbing in vmstat means for a *data
loading* job on this machine (the "slow CSV load" diagnosis from
Lesson 3 §5).

Cleanup: after `churn.sh` exits, `rm ~/lab24/churnfile` (200 MB of
scratch has no future) and confirm with `df -h ~`.

## Round 3 — replay history with sar (10 min)

sysstat's collector may be disabled by default (M24 Lesson 3 §6).
Either wait for samples as root-enabled, or — the lab's honest path —
**generate your own history** by capturing to files as you go:

```console
$ sar -u 2 30 > ~/lab24/sar-cpu.txt &     # runs ~1 min; start BEFORE load
$ ./burn.sh 90
$ wait; cat ~/lab24/sar-cpu.txt | tail -8
```

(If the sysstat service *is* enabled, also show:
`sar -u | tail -12` — the day's recorded history.)

**Interpret to write:** the `%user` column's arc across the file —
where load starts, peaks, ends — and one sentence on why *replayable
history* beats live-only watching for the "it was slow at 14:20"
class of tickets.

## The 60-second health check — under load (5 min)

With one more burn round running, execute Lesson 3 §8's five-command
check and time yourself. Target: under 60 seconds, each command's
verdict noted in one line. This is the dress rehearsal for
[Mini-Project E](../mini-project-health-backup-kit.md), where the
check becomes `health.sh`.
